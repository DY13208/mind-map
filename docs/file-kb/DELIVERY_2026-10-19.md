## 3. 批次模型

仍是一条 `kb.jobs` 队列。007 只增加 `kb.batches`、`kb.batch_items`、`kb.job_attempts`，以及 jobs 上的 `batch_id`、`resource_class`、`first_started_at`、`metrics`。领取使用事务级 advisory lock 加 `SKIP LOCKED`。结构阶段优先于解析，避免 100 个解析任务把收尾饿死。

状态：`accepting / running / paused / cancelling / done / partial / failed / cancelled`。库里的 control 只有 `running / paused / cancelled`，终态由条目计数推导。

- 暂停：不打断已领取的租约和事务，下一阶段不能再被领取。
- 取消：只取消尚未领取的任务。正在解析的文件会写完原始结果，但不再入结构队列。正在提交的结构事务会跑完。
- 失败重试：复用原来的 job 和 run，新租约；`kb.job_attempts` 保留每次租约、耗时和错误。
- 上传失败的条目没有 run：重试会重新打开上传，客户端用同一个 `client_key` 再传再封口。
- 相同 `client_key` 重放是幂等的；同一个 key 换文件返回 409。内容重复链接到已有 run，不再生记录。

接口、字段和前端上传顺序写在 `docs/file-kb/BATCH_API_V2.md`。本轮没有改 `/kb` 页面。

指标在 `services/file-kb/src/metrics.js`：排队等待、本次等待、解析/结构化耗时、数据库耗时、进程 RSS 采样、进程 CPU 增量、失败原因。RSS 和 CPU 是进程级采样，不是单文件独占值。容器峰值以实验室 `docker stats` 为准。

默认配置仍是：

```text
KB_WORKER_CONCURRENCY=2
KB_LIGHT_CONCURRENCY=2
KB_HEAVY_CONCURRENCY=1
KB_FORMAT_CONCURRENCY={}
KB_MAX_QUEUED_PER_USER=50
KB_NATIVE_LIGHT_PARSE=false
```

轻任务是结构化，以及 xlsx/md/csv 解析。其余解析（含 PDF）是重任务。全局并发和轻重上限同时生效，所以 `heavy=2` 只有在全局槽也是 2 时才能同时跑两个 PDF。

## 5. 推荐配置

不要把全局并发调到 2 以上，也不要宣称解析变快了。同一套 final/balanced 上限，100 文件一轮 189 秒、下一轮 333 秒。差在 Docling：实验室容器峰值约 1.4GiB，CPU 可以到 300% 以上，同规格 PDF 的尾延迟从大约 12 秒摆到 26 秒。

已经能确定的只有上传侧：队列上限 50 时，100 个文件上传被 429 挡住 179 秒、背压 1018 次。上限改到 100 后背压为 0，上传 8.5 秒和 30 秒。浏览器应先建批次、并发 2 上传、遇 429 等待 `retryAfterMs`，封口后轮询，不要在一个请求里等解析。

建议部署值：

```text
KB_WORKER_CONCURRENCY=2
KB_LIGHT_CONCURRENCY=2
KB_HEAVY_CONCURRENCY=1
KB_MAX_QUEUED_PER_USER=100
KB_NATIVE_LIGHT_PARSE=false
KB_DOCLING_OCR=false
```

`heavy=1` 保持基线的「最多一个重型解析」行为。`KB_MAX_QUEUED_PER_USER=100` 是上传背压的实测修复，不是解析加速。原生轻解析会改走 ExcelJS / 原生 Markdown，输出形态和 Docling 不同，默认保持关闭。

压测期间 `http://127.0.0.1:8990/api/health` 在 balanced-100 与 final-100 全部返回 200。final-100 有一次健康检查到 1926ms，不能把它单独归因于 File KB。实验室没有使用正在跑的 `mind-map-file-kb-worker-1`。
