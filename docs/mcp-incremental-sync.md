# MCP 增量写入与可靠同步

实施分支：`codex/mcp-incremental-sync`，基准代码：`0160b5a7`。

## 边界

- 首版优化 MCP 身份发起、明确 UID/root 引用的新增、普通字段更新和删除。
- 标题/路径、移动、附件业务、TODO/SOP 批量、整图替换和版本恢复保留既有路径。
- 保留现有工具与操作粒度，不增加批量工具，不重构布局引擎。
- 所有压测、故障注入与迁移只在 `mcp-incremental-test` 独立 Compose 项目执行；生产发布保留人工确认。

## 阶段记录

| 二 | 双逆操作格式与连续性/快照恢复 | 7项单测、5项隔离PG HTTP/Socket集成通过 |
| 三 | 持久日志事件桥、按序补齐、重连和活跃房间核对 | 针对性测试和隔离PG/Redis双实例Socket回归通过；未做完整故障矩阵 |
| 四 | 轻量 meta、UID Direct、幂等及背压 | 12项有效单测及Direct提交/归档幂等PG回归通过；MCP HTTP新增、重试、跨实例事件通过，其余HTTP缺项见交付报告 |
| 验收 | 同环境性能对比、完整故障矩阵、人工复测 | 根据用户快速完成要求暂缓；不得宣称性能门槛通过 |

阶段一失败用例：旧 nodes 格式不能经 Direct 完整恢复子树；Direct rows 格式不能经 HTTP 慢路径恢复；Socket 对缺失版本仍返回 reload:false；客户端恢复规划器会跨小版本缺口应用数据。

用户后续明确要求“快速完成修复，不要过度校验”。据此停止反复UI校准和长压测，冻结现有有效样本；核心修复并行实施，保留必要的恢复、幂等与双实例回归。未完成的全量性能验收继续明确列为缺项，不宣称已通过；生产部署仍待人工确认。

阶段一首次正式运行 `baseline-0160-20261012-formal` 在写入计时前停止：13个页面均连接V2，但其中一个仅渲染根节点，结构校验只有12/13通过；该次运行没有100节点计时样本，不能计入性能基线。保留原始页面指标和失败截图。后续采用最多4页同时初始化，13页全部在线且结构就绪后才开始计时；优化后必须使用相同加载波次，LCP结果不代表13页同时冷启动。

隔离环境关闭登录鉴权时，已有MCP请求的actorId为anonymous。增量策略需要独立核验服务器端MCP凭证识别，验证实际提交路径；不能根据客户端ID前缀分流，也不能在同轮测量中途变更鉴权配置。

第二次运行 `baseline-0160-20261012-wave4-v2` 完成7轮700次写入（无错误、每轮版本增加100、无额外操作），在第8轮写入前因一个客户端根节点越出视口而停止，仍不是完整基线。测试工具改为每页点击产品已有“回到根节点居中”按钮并记录前后几何，真实单页验证房间版本1→1；之后所有正式基线和优化轮采用同一归中协议，保留失败样本和加载期LCP，不修改布局引擎。可见性观察组固定appB，奇数轮为A→B，偶数轮为B→B，报告按方向区分，另补A→B和B→A验证。

可见性测量边界：正式负载的新增节点插入根节点末尾，可能被SVG裁剪；DOM探针未见文字不能单独证明漏广播，也不是有效的可见延迟样本。需同时报告权威提交、客户端op:event接收、客户端图状态、DOM渲染与视口可见。归中正式运行第1轮的appB观察组在100次已提交写入窗口内每页捕获到0条op:event，这是通知缺口证据；DOM超时则保留原因未区分。补充双向探针时使用可见夹具或产品真实定位操作，不伪造节点DOM。

## 兼容与数据规则

- 房间版本本来已共用一条数据库序列；本次修复的是提交后的事件与恢复链路。
- 先支持两种历史逆操作格式，再开放新写入；不重写历史 JSON。
- 在线与归档操作通过单条 SQL、同一 MVCC 快照读取；归档仍保留时允许补齐，真正缺版本时要求权威快照，不发送失败页中的部分操作。
- 幂等只承诺仍保留的操作记录。稳定 ID 的不同身份、不同业务输入不得复用；没有请求摘要的旧记录返回明确冲突，不重新执行。
- 正常 meta 读取仅取元数据；空标题可有界读取根节点文字。极少的旧房间若既无标题又没有初始化节点表，保留原慢路径以兼容旧标题语义，并单独计量，不能纳入 UID 性能提升口径。
- 已提交旧操作的重复请求不能回退当前版本缓存或恢复 epoch。
- 关闭登录鉴权时，服务端验证MCP凭证后仅设置内部来源标记，保留旧anonymous业务actor；不改变旧历史操作者校验。幂等身份使用已验证principal，与业务actor分离，防止不同MCP凭证在anonymous模式下共用操作ID。开启登录鉴权时沿用现有authUser和权限行为。
- MCP队列保留每房间1/实例4在途、等待数100/1000和30秒等待上限，另设64MiB等待payload估算字节上限；超限返回同一可重试繁忙错误，不缩小既有单次输入合同。字节预算仅计等待任务，开始执行、超时、取消及时释放；活动payload另受4个任务和既有单次体积上限约束。估算不含JS对象/网络缓冲开销，不能宣称精确heap上限。

## 操作兼容矩阵

| 调用类型 | 本轮提交策略 | 必须保留或验证的语义 |
| --- | --- | --- |
| MCP明确UID/root的新增 | 通过公共校验后Direct | 服务端生成UID、父节点墓碑、位置、SOP、标准事件和逆操作 |
| MCP明确UID的普通更新 | text/note符合准入时Direct | 字段版本、权限、SOP、恢复epoch；非普通字段回到原路径 |
| MCP明确UID的删除 | 通过公共校验后Direct | 根节点保护、子树墓碑、完整逆快照、晚到请求 |
| 标题/路径引用 | 原路径 | 重名与解析错误原样返回，不猜目标、不自动拆分 |
| 移动/重排 | 原路径 | 父子关系、位置、并发冲突及逆操作 |
| 附件与expected条件更新 | 原路径 | 替换冲突、删除后写回保护和历史资源保留 |
| TODO/SOP业务批量 | 原路径 | 业务校验、审批、事件与审计语义；不新增隐式重试 |
| 整图替换/VERSION_RESTORE | 原路径并可靠通知 | 快照恢复、恢复epoch、旧baseVersion保护 |
| 浏览器操作 | 既有collabV2 | ACK保留，事件发送统一；不进入MCP队列 |
| 历史撤销/重做 | 共享兼容恢复边界 | 同时读取旧nodes和Direct rows，不改历史记录 |

## 数据库说明

不新增数据库字段。阶段四需要给归档操作表增加 `(room_key, operation_id)` 非唯一查询索引，并交付独立升级/回滚脚本。索引只在隔离环境执行，生产不自动运行。归档搬表已经是原子事务，不为此新增归档房间锁。

## 验收口径

相同6001节点夹具、环境及仪表：UID/root 单节点 P95 和连续100节点总耗时均不高于基线50%；13浏览器展开/收起 P95 退化不超过10%；节点、父子顺序、墓碑、版本与恢复一致性全部通过。

同时记录 P50/P99、真实锁等待、锁获取 SQL 往返、事务、提交后缓存、可见延迟、长任务、CPU/内存与补偿次数。未测项显式标注，不能以SQL往返冒充锁等待，也不能以Socket客户端替代浏览器。

原始样本保存在测试目录的 results 中，不纳入源代码提交；交付时提供可复现命令、运行版本和结果摘要。发布前只完成可审查产物，不自动部署或重启生产服务。
