# 分散登记的脑图审批流程

2026-10-20。本次将请假试点扩展为通用的**顺序审批**。模板可以放在任意有权限的脑图节点下，不要求固定目录或固定房间。请假保留专用工作时段/假种规则，其他流程采用各自登记的字段和审核要点。

## 如何登记一类审批

在实际制度节点下增加一个直属子节点 `流程标识：名称或编号`，例如下面这棵树。字段、流程和人员都直接写在节点中，不用备注或另填配置表单。

```text
合同签约审批
  流程标识：contract-sign
  触发词
    签合同
    合同签约
  申请字段
    合作方〔必填〕
      类型：文本
    合同金额〔必填〕
      类型：金额
      最小值：0
    预计签订日期〔必填〕
      类型：日期
    业务联系人〔必填〕
      类型：成员
    合同文件〔必填〕
      类型：附件
    其他说明〔选填〕
      类型：文本
  审批流程
    法务审核
      审核要点
        在这里登记实际制度的通过条件与依据，不填虚构标准
    业务负责人
      审核要点
        在这里登记实际负责人需要核验的业务事实
  审批配置
    法务审核
      账号：实际成员ID
    业务负责人
      部门：实际部门ID
        账号：该部门审核人ID
    抄送
      业务经办人
        账号：实际成员ID
  抄送
    业务经办人
```

这是登记格式示例，角色与审核要点由实际制度负责人确认，不能把示例当作已批准的制度。

- 模板根节点、直属“流程标识”节点各自保留稳定 UID；同名模板可分布在不同位置，系统展示来源让申请人选择，不按第一个结果执行。
- `申请字段` 也可命名为 `必要条件`。字段默认必填；不必填的字段标 `〔选填〕`。支持文本、多行文本、日期（YYYY-MM-DD）、日期时间（明确日期和时刻）、数值/金额、成员、附件、选项。选项型字段下加 `选项 → 每个允许值`。
- 数值可登记 `最小值：...`、`最大值：...`；字段和步骤最多分别50项、20步。未登记的外部余额、资质、合同真实性等仍由实际审核人核验，不能把申请人自填值当作外部系统证明。
- “审批配置”里的角色必须和“审批流程”里的步骤同名。按部门配置时，使用组织架构中真实的部门ID；无匹配、多人匹配或账号失效会提示待配置。
- 有模板管理权限的人员在编辑器选中模板或其子节点，点击“配置审批流程”，核对后发布。人员、审核要点、字段或规则变化后需要重新发布。MCP没有代替人工发布或正式审批的入口。

## 右键节点提交审批流

右键流程节点，在“蒸馏skill”下点击“提交审批流”。系统定向读取该节点，不按名称选择其他模板。
直属的“提交要求”分支可作为申请字段定义；字段默认必填，类型和选填标记沿用上述规则。
没有填写提交要求时会提醒补充；已有要求但本次资料未填完整时，会逐项提示并阻止正式提交。

直接选中的“提交要求”流程无须另加流程标识，但不会因此进入模糊匹配目录。
右键入口直接核对原流程“提交要求”分支，不创建同级申请或资料骨架。
支持“提交要求 → 员工 → 具体人员 → 姓名”、“具体日期 → 日期”以及“评分表附件 → 附件节点”。
填写完整后在核对页确认提交；姓名、日期和附件属于本次材料，规则指纹只包含字段结构、类型、
审批规则及人员配置，填写值不触发重新发布。正式申请与历史仍独立保存，已提交材料采用固定快照。
原有通过明确申请意图或目录发起的独立申请入口继续兼容。
原节点上的申请撤回或完成后，可在同一原节点重新发起；新旧申请独立留存历史，不要求新建脑图节点。

对于明确登记直属规则“发起后全部流程默认同意”的流程，管理员发布后，完整且确认提交的申请
直接记为已通过，再通知申请人及已配置的抄送人。历史保存自动同意的规则UID、原文和发布指纹，
不生成或伪造人工审批决定。没有这条明确规则的流程继续走人工顺序审批。
“抄送人事组、IT”这样的直属节点可声明抄送角色；具体账号仍在“审批配置 → 抄送 → 角色 →
账号：真实成员ID”中绑定，未配置不发送通知也不允许提交。草稿、缺项和重复请求不产生重复通知。

如果抄送分支直接写真实姓名（例如“抄送张某、李某”），没有显式角色配置时按本企业成员表精确匹配。
仅唯一同名成员可自动绑定；同名多人须指定成员ID，没有成员记录须先同步通讯录。跨企业成员不参与匹配。
解析出的抄送账号也计入发布指纹，成员匹配发生变化后必须重新发布，避免静默更换通知接收人。

## 怎样发起和办理

1. 用户在自己的业务节点下**新建一个独立申请子节点**，例如“我要签合同”“我要关停渠道”“我要请假”。每个申请节点绑定一个流程，避免复用历史申请的资料。
2. 系统在当前身份可查看的模板中按名称/触发词匹配。一个候选生成草稿；多个候选显示来源供选择。没有匹配词时可分页选择现有流程，未登记则提示待配置。普通SOP、例子和任意节点名不会自动变成可执行审批。
3. 在生成的 `申请资料 → 字段 → 待填写` 节点中直接编辑值，也支持 `字段：值`。附件上传到模板指定的附件字段节点或其子节点。原有直接登记的字段会保留，不强行搬进另一个表单。
4. 缺项、基础校验和人员配置情况显示在“填写检查”节点。提交页只读核对这些资料；修改尚未同步、模板/人员变化或核对后的资料变化，会要求重新读取和核对。
5. 用户明确确认后提交，按已发布版本逐级通知审核人。审核人查看该流程自己的要点、AI建议和材料，填写判断依据并通过、退回或拒绝；抄送只在最终通过后通知。
6. 最终状态回写申请子节点，历史和每轮判断依据保留在“我发起的 / 我已审批”中；修改“已通过”文字不会改变正式决定。

## AI / MCP

右键“发布这个审批流”把该节点注册为 Agent 审批定义，而不是创建申请。发布保存规则指纹和整棵子树内容指纹；节点显示“审批”，通过“复制给AI”生成带 `expected_definition_version` 的 MCP 执行指令。只有个人 MCP 可准备执行此定义，普通网页入口用于发布与人工处理。`template` 后调用 `prepare(use_source_node=true, expected_definition_version=publication.id)`，`evaluate` 只读返回 `execution.mode` 与 `handoff` 的实际账号、姓名和 @ 提示；`submit` 仍携带节点哈希、当前版本和明确提交确认。自动规则或现有AI预审配置能够处理时由引擎执行，无法核验/置信度不足/模型异常时保留实际审批人的待办并发送站内通知，不把 @ 文本冒充企微送达回执。

修改该节点或子节点内容（含填写值、附件、备注等）后，审批定义变为草稿并显示“审批·草稿”；展开收起不会改变发布状态。旧版本即使内容被改回也不能自动复活。已复制的旧指令和旧草稿不能绕过后端版本校验；重新发布后只允许显式准备最新版本，旧的在途申请须先处理。该生命周期只适用于新入口发布的 `agent_mode` 定义；已有普通审批历史及旧的本次规则确认模式保留兼容。定义状态按房间权限分页读取，标记是只读展示，不把渲染标签写回用户脑图内容。发布仍须有管理权限且人员配置完整；Agent不能擅自发布流程。

通用审批无需强制先做全局发布。首次执行或模板变化时，Agent展示字段、完整规则、审核人与抄送人，取得用户明确的规则确认和提交指令后，`submit` 同时传 `confirm_rules: true`、`expected_policy_fingerprint`（最新 `policy_fingerprint`）、`confirm_submission: true`、当前版本和节点哈希。此确认以 `rule_confirmation.scope=request` 记录在本次申请与审计中，不将模板全局发布给其他人，也不放宽原节点编辑权限；旧的管理员全局发布功能仍可使用。请假专用流程保留原有发布要求。未确认、指纹变化、材料变化或人员缺失均阻止提交。

原流程的直属角色（例如“SSC”）包含“默认同意／以下情况拒绝／须确认”分支时，可直接解析为顺序人工审批步骤；上下文保留在各审核要点中。自然语言例外（真实性、金额是否错误等）不由Agent自动推断，交由实际绑定的审核人逐项核验。只有独立且无冲突的“发起后全部流程默认同意”规则可自动通过；该规则与角色拒绝／须确认条件同时出现时阻止执行。角色仍须绑定真实账号；系统不凭“SSC／副总”等职务名称猜人。

用户已指定原流程节点时可直接调用 `approval_request.template`，无需再做意图匹配。若返回 `supports_source_node_input=true`，调用：

```json
{
  "action": "prepare",
  "room_key": "room-vm1hdcce",
  "node_uid": "ee670f4b-bf45-4522-b568-3eb759af8be5",
  "template_source": {
    "room_key": "room-vm1hdcce",
    "node_uid": "ee670f4b-bf45-4522-b568-3eb759af8be5"
  },
  "use_source_node": true
}
```

此模式直接绑定原“提交要求”，不新增申请分支，仍要求原节点编辑权限及模板来源一致。`import` 读取最新材料；核对字段、附件、`cc_resolved`（实际账号、姓名、组织及解析来源）和 `validation.configurationRequired` 后，经用户明确确认再提交。`auto_approve` 表示原模板规则，不能由Agent凭文字伪造决定。`source_node_input` 标明当前草稿使用的模式。

`submit` 及 `status` 返回独立的 `hrms_sync`：`pending` 等待、`failed` 自动重试、`synced` 已同步，包含 `result.application_no`、`last_error`、`synced_at`；null表示未入队，不可把审批通过当作人事同步成功。抄送名单在大响应摘要中最多保留10人（普通响应30人），用 `cc_resolved_count`/`cc_resolved_truncated` 明示是否截断；敏感连接凭据和内部同步payload不返回。部署后客户端需重新连接MCP以刷新参数和工具说明。

新增通用工具 `approval_request`：

- `resolve` 匹配意图；`catalog` 分页发现可访问模板，`hasMore=true` 必须继续 `nextCursor`，不能只读第一页就判断唯一匹配。
- `template` 读取所选模板的实际字段、稳定key、来源和审核步骤。
- `prepare` 必须带所选 `template_source`，不默认路由到请假。它只生成草稿与节点，不发送审批待办。
- AI经用户授权写申请资料节点后，`import` 读取权威数据；展示最终资料并取得明确提交指令后，`submit` 携带当前版本、节点指纹和幂等操作ID。
- `analysis` 只记录辅助建议；`status` 查询正式结果。没有MCP代批入口。结果未知先查询，不能换操作ID盲目重复提交。
- 原有 `leave_request` 和旧接口保留兼容；通用界面与新工具通过显式模板来源工作。客户端需重新连接以发现新工具。

## 实现与运行

已通过的“转正申请表”可通过 `HRMS_SYNC_ENABLED=1` 与独立的 `HRMS_SYNC_*` 连接同步至人事系统 Approval Instance（已通过）。同步保留字段、已核验的原附件、流程规则和外部审批证据，不伪造人事系统人工审批任务，不自动填写实际转正日期。人事仍按其原有“确认转正”流程办理员工主数据变更。

同步单的展示流程必须包含有效的 start/end 节点，人事详情接口会校验 `process_snapshot_json`；不能写空 nodes。原脑图规则与审批证据保留在外部快照及 hook_result 中，不据此创建虚假的人工审批任务。`scripts/hrms/verify_approval_import_detail.py` 在本地站点回滚验证新导入、历史修复、幂等重试与真实详情接口兼容性。

人事详情的“审批流转”通过 `scripts/hrms/approval_external_timeline.py` 只读投影原始外部审批证据，展示发起、实际人工决定或规则自动通过，以及抄送名单；没有人工决定的自动流程不能显示为某人已审批。抄送名单不冒充人事端通知回执，也不创建可操作任务或扩大单据查看权限。人事源码的接入点由 `scripts/hrms/install_external_timeline.py <employee_roster包目录>` 安装并备份；已有导入单自动适用，无需重建单据或重发通知。后续同步额外保存同企业人员的企微账号与显示姓名，历史单据从提交快照读取抄送身份。

审批事务内写入 `approval_hrms_sync` 持久队列，后台每15秒处理，失败指数退避重试，最大间隔1小时；页面显示状态和返回单号。来源请求ID+轮次在人事端生成确定性唯一单号，相同内容重试返回原单，内容冲突拒绝覆盖。附件传实际字节并在两端校验SHA256，限制10份、合计20MB；附件变化时失败，不将新文件冒充原审批材料。历史单据不会批量自动补发，须明确选定来源请求入队。

HRMS接口源码在 `scripts/hrms/approval_import.py`，专用身份初始化在 `scripts/hrms/setup_approval_importer.py`。该角色无通用文档CRUD权限，仅通过限定接口导入本公司已通过转正单；站点配置 `wcpd_approval_corp_id` 限定来源企业。不得将组织查询账号改为写入账号。部署包含 `hrmsSync.js`、service、storage启动逻辑及前端；同步配置应持久注入应用环境。

抄送节点中的“对应HRBP”按提交要求内的员工姓名、编号或企微账号查询人事系统，使用员工主部门登记的 HRBP；主部门未登记时向上查找，重名、不在职或缺失企微账号时阻止提交。“IT”默认精确绑定同企业的 `LiJiBing`，可由 `WCPD_APPROVAL_IT_USER_ID` 配置。提交窗口展示实际人员及来源；核对后组织人员变化时要求重新读取。

连接使用独立的 `HRMS_ORG_*` 配置。Frappe 端只读接口源码在 `scripts/hrms/approval_directory.py`，部署至 employee_roster.integrations；`scripts/hrms/setup_org_reader.py` 是当前本地站点的初始化脚本，执行前应核对其中站点、公司及企微企业 ID。专用角色不授予 Employee/Department 文档 CRUD 权限，接口按公司 User Permission 检查范围，仅返回员工部门与已登记 HRBP 的必要身份字段。凭据只能存于忽略的环境文件或密钥存储，禁止提交到版本库。

沿用现有认证、脑图权限、审批存储、版本、事务、消息/SSE、历史和可信节点写入，不改附件存储/上传/下载接口，不新增依赖。

模板发现使用 `room_nodes` 中明确的“流程标识”元数据及部分索引，分页读取名称/触发词；不拉取整张脑图。选定流程后才定向读取最多500节点的模板子树。普通成员只能发现自己有权查看的模板；正式审核人按本次申请授权查看固定材料，无须获准查看申请人的整张脑图。

发布部署包括协作服务、MCP服务和前端；启动自动建立元数据发现索引。现有请假历史无需迁移。模板可以新建在不同位置并即时发现，不需要每新增一类顺序审批都增加代码。

**当前支持顺序审批。** 条件分支、并行、会签、或签等尚未实现，会阻止发布或提交，不会静默当作顺序执行。自然语言业务判断仍由AI辅助与人工核验；吉客云、金蝶的建单/审核动作不在本次范围。

- 前端异步/意图/歧义选择与既有通知回归通过。浏览器验证渠道节点填写→只读摘要（零资料输入框）→渠道负责人通过→结果回写；另验证合同7项字段、请假字段及多候选明确选择。桌面和390px选择器无横向溢出，控制台无错误。浏览器使用实际MindMap及真实HTTP/PostgreSQL，身份和AI为隔离夹具。
